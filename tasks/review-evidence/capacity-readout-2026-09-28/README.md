# Bounded operational capacity readout

The existing Ops operations expose current configuration but cannot measure historical execution overlap or Cloud SQL connection samples. `capacity-readout` adds one manually dispatched, read-only inspection of a past UTC window of at most two hours. It uses the existing WIF identity and checksum-pinned Cloud SQL proxy. It does not start a job, generate load, change settings, grant permissions or call a model.

The Cloud Run scope is the eight production jobs in us-west1. Each execution retains its actual start/completion, task count, parallelism, retries and image; missing start uses creation only as an explicitly uncertain inclusion bound. Each API query has a five-page cap, a ten-second request timeout and an eight-MiB response limit. Partial results, denial and empty successful responses remain distinct. Logging retains only time, severity, resource identity and two pool-error signatures, never message text, request URLs, environment values or trace exemplars. The SQL transaction is read-only with a 15-second statement timeout and two-second lock timeout. It reports current reserve/settings and backend counts separately from historical job outcomes; the latter has a 1,000-row limit and explicit truncation flag. A stale unfinished ledger row is not evidence of an active execution.

## Use and interpretation

After release, dispatch Ops with operation `capacity-readout`, `capacity_start=2026-09-28T05:55:00Z` and `capacity_end=2026-09-28T07:10:00Z`. Inspect the retained artifact and workflow steps together; a green workflow cannot turn `http_403` into measured absence. The existing WIF Logging probe returned permission denied before this implementation. No IAM grant is part of this change. Use `describe-service` and `describe-jobs` separately for current configuration. Current configuration/snapshots do not reconstruct historical worker commands or reserve.

Cloud SQL's connection metric has a database label and is sampled every 60 seconds. Reassemble paginated series and match timestamps before summing across databases; never sum each database's independent maximum. Retain gaps and report a sampled maximum, not an instantaneous peak. Request-count samples can straddle the requested window; latencies retain their original distributions and intervals rather than a fabricated global percentile. Request metrics do not cover requests that never reach the container, and latency excludes startup. API execution history has finite retention. The receipt alone establishes neither safe invitation volume, worst-case connections, SEC egress nor provider capacity.

API references: [executions](https://docs.cloud.google.com/run/docs/reference/rest/v2/projects.locations.jobs.executions/list), [Monitoring](https://docs.cloud.google.com/monitoring/api/ref_v3/rest/v3/projects.timeSeries/list), [Cloud SQL metrics](https://docs.cloud.google.com/sql/docs/postgres/use-system-insights), [Logging](https://docs.cloud.google.com/logging/docs/reference/v2/rest/v2/entries/list).

## Verification

The offline collector gate exercises continued pagination, a repeated continuation, an explicit page cap, denied metrics, empty successful metrics, unknown execution intervals, out-of-fleet jobs/regions, and payload redaction. One committed-state mutation stops at the first page; the test must fail on its lost second page, then pass on restoration. A disposable PostgreSQL 15.15 fixture checks the real query's read-only state, missing optional PostgreSQL setting, numeric-only counter retention and explicit 1,000-row truncation. Full local/hosted gates and exact-head review are recorded in the PR before release.

Independent review raised the initial all-job/all-region query scope. Two fresh refutation passes upheld it. The correction uses fixed job/region queries plus local retention checks; the SQL ledger uses the matching eight business names. No locked test, application runtime, schema, pricing, prompt, flag or dependency is changed.
